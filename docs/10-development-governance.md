# 开发治理与防跑偏机制

## 1. 文档层级

发生冲突时按以下优先级处理：

1. 已接受 ADR：解释为什么采用某项长期约束。
2. 产品章程与功能范围：决定是否应该做。
3. 架构与 Runtime 规范：决定责任属于哪里、状态如何变化。
4. 当前里程碑实施计划：决定本轮具体做什么。
5. 代码和测试：描述当前真实行为。

如果代码与文档冲突，先确认是实现缺陷还是决策变化。不得只改其中一侧让冲突暂时消失。

## 2. 每个里程碑的文档包

开始里程碑前创建：

```text
docs/plans/<milestone>/
  00-goal.md
  01-behavior-scenarios.md
  02-design.md
  03-task-breakdown.md
  04-acceptance.md
  05-progress.md
  06-closeout.md
```

要求：

- Goal 只描述用户可观察结果。
- Behavior Scenarios 包含正常、中断、拒绝和失败路径。
- Design 明确接口、事件和持久化变化。
- Task Breakdown 中每个任务可以独立测试。
- Acceptance 给出可执行命令和预期结果。
- Progress 记录事实，不写模糊完成百分比。
- Closeout 记录实际交付、偏差、遗留风险和下一里程碑输入。

## 3. 变更进入流程

```text
提出用户行为
  -> 检查是否属于 P0/P1/P2
  -> 检查是否违反 ADR
  -> 写一个失败场景
  -> 确定新增事件和状态
  -> 写测试
  -> 实现最小切片
  -> 运行故障测试
  -> 更新文档和演示
```

如果无法写出失败场景或验收测试，该功能还没有设计完成。

## 4. PR/任务检查表

- [ ] 是否服务当前里程碑？
- [ ] 是否新增第二套 Agent Loop？
- [ ] 是否新增 Session 之外的事实真相？
- [ ] 是否让 UI、Tool 或 Provider 反向依赖 Runtime 实现？
- [ ] 是否定义了错误、取消、超时和恢复行为？
- [ ] 是否经过权限和 Workspace 边界？
- [ ] 是否会泄漏 Secret 或扩大日志内容？
- [ ] 是否有 Fake 驱动的确定性测试？
- [ ] 是否更新真实入口对应的设计文档？
- [ ] 是否增加了仅服务一个调用方的抽象层？

任一高风险项无法解释时，不合并。

## 5. 复杂度预算

每个里程碑 Closeout 记录：

- 主体 Python 文件数和行数；
- 最大十个模块；
- RuntimeRunner 行数；
- Event 类型数量；
- Tool 数量；
- 核心依赖数量；
- 单元、集成和场景测试数量。

触发架构复查的信号：

- RuntimeRunner 超过约 800 行且职责无法独立命名；
- 一个模块超过约 1,000 行；
- durable SessionEvent 类型超过 14 个；
- P0 Tool 超过 8 个；
- 同一事实由两个存储分别写入；
- 同一 Provider 请求在两个位置构造；
- UI 需要访问 Runner 私有字段；
- 为单一实现创建超过两层转发抽象。

这些是复查信号，不是机械拆文件指标。拆分必须基于责任边界。

## 6. 演示驱动验收

每个版本保留一个不依赖网络的 Fake 演示和一个可选真实模型演示。

Fake 演示证明控制流确定；真实模型演示证明系统具有实际可用性。两者不可互相替代。

v0.1.0 最终演示固定为：

1. 阅读并解释一个小仓库。
2. 修改一个有测试的缺陷。
3. 在权限确认处退出并恢复。
4. 触发一次工具输出外置和上下文压缩。
5. 显式保存并在新 Session 中检索一条项目记忆。

## 7. 决策冻结点

M1 closeout/首次公开发布前必须确认：

- 项目名、Python 包名和 CLI 命令；
- 首个真实 Provider 的兼容目标；
- 许可证。

开始 M7 前再确认最终 UI 是 Textual TUI 还是增强型 Rich REPL。M1 至 M6 的运行时不能依赖该选择。
